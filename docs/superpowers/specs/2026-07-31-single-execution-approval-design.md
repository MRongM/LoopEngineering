# Loop Engineering 单次执行授权设计

- 状态：用户已批准设计方向
- 日期：2026-07-31
- 适用范围：Codex Adapter 的任务准入与执行前人工门禁
- 基线：Loop Engineering Core Protocol 0.1.0

## 1. 问题

当前 Codex Adapter 在状态变更任务开始前可能依次询问控制模式、Loop
Contract、设计和实施计划。`collaborative` 模式因此产生多次语义重叠的确认，
与既有设计中“AI 起草完整契约，用户一次批准后自动执行”的目标不一致。

## 2. 目标

一次执行授权应覆盖开始实施所需的完整决策，同时不削弱运行期间的安全门禁：

1. 未显式指定模式时直接采用 `collaborative`，不单独询问模式。
2. 在只读调查后一次性展示可执行契约摘要。
3. 用户批准该摘要后，设计、计划和普通实施连续进行，不再分别等待确认。
4. 范围或权限变化、未预授权危险操作、生产访问和敏感数据操作仍暂停。
5. `collaborative` 与高风险任务的最终人工验收保持不变。

## 3. 非目标

- 不把默认模式改为 `autonomous`。
- 不取消 Loop Contract、证据、Checker、预算或最终验收。
- 不放宽生产访问、敏感数据、自动合并、部署、强推或历史改写限制。
- 不改变 Core 的状态机、Schema 或既有契约兼容性。
- 不把安装、卸载或 Git 操作变为隐式授权。

## 4. 交互契约

### 4.1 模式解析

Adapter 按以下顺序解析模式：

1. 用户显式指定 `collaborative` 或 `autonomous` 时采用该值。
2. 用户未指定时采用 `collaborative`。
3. 解析出的模式写入执行契约摘要，由同一次执行授权批准。

只有在用户表达无法可靠映射到任一模式、且该差异会实质改变授权范围时，
Adapter 才提出一个聚焦的澄清问题。模式不会从上一个任务继承。

### 4.2 单次执行授权

Adapter 完成只读调查后，展示一个 `Ready-to-execute Loop Contract` 摘要，顺序为：

1. 模式、目标、范围和明确排除项。
2. 验收条件与验证命令。
3. 非简单任务的关键设计决策与最小实施步骤。
4. 风险级别、权限、精确 Git 目标和预算。
5. 已预授权操作、仍会触发暂停的条件和停止条件。

摘要末尾只提出一次执行授权请求。批准后记录 `contract_approval`，进入设计或
计划状态并连续推进到执行；默认契约不包含 `design_approval` 或
`plan_approval`。现有契约或项目规则显式声明这两个额外门禁时仍按声明执行，
以保持兼容。

如果用户拒绝或修改摘要，Adapter 重新起草一个完整摘要；新的批准替代旧草案，
不得把多个局部答复拼接成隐式授权。

### 4.3 执行后的暂停条件

已批准契约内的普通文件修改、验证和精确预授权操作不再询问。以下事件仍暂停：

- 目标、仓库、允许路径、验收条件、危险权限、Git 目标或预算实质变化。
- `gate check` 返回 `pause` 的未预授权危险操作。
- 生产环境访问或敏感数据操作。
- 来源不明的用户改动与当前任务冲突。
- 必需证据或外部授权无法获得。

精确预授权不能覆盖协议永久禁止的自动合并、部署、强推和历史改写。

### 4.4 最终验收

最终验收发生在执行和验证之后，不计入“执行前确认”。`collaborative` 和所有
高风险任务继续要求 `final_acceptance`；`autonomous` 的低/中风险任务可在无需
最终人工验收的情况下进入 `DONE`。中高风险任务继续要求独立 Checker。

## 5. 组件边界

本次行为变更限定在 Codex Adapter 及其契约测试：

- `adapters/codex/SKILL.md` 定义单次执行授权的正向交互配方。
- Adapter 契约测试锁定默认模式、摘要内容、一次执行前批准和保留的风险门。
- 已批准协议设计更新协作模式说明，消除“契约、设计、计划分别暂停”的旧描述。

Core 现有 `contract_approval`、可选 `design_approval`/`plan_approval`、
`dangerous_action` 与 `final_acceptance` 数据模型保持不变。这样既收敛默认交互，
也不破坏已有契约或需要额外阶段门的项目。

## 6. 错误与歧义处理

- 缺少可安全假设的信息时，一次只问一个会阻塞契约起草的问题；这属于需求澄清，
  不是授权确认。
- 可公开的低风险假设写入摘要，不额外询问。
- 危险目标不精确时不得预授权；目标解析后再走危险操作门。
- 用户批准后出现范围漂移时，生成完整的新版本摘要并只请求一次修订授权。
- Adapter 不得用“减少确认”为由跳过平台或仓库要求的强制门禁。

## 7. 验证策略

### 7.1 行为场景

使用同一组压力场景比较修改前后行为：

1. 未指定模式的非简单功能任务，同时包含设计和计划压力。
2. 明确 `autonomous` 且包含精确 Git 预授权的任务。
3. 已执行后才出现未授权危险操作的任务。
4. 项目显式要求 `design_approval` 的兼容性任务。

期望结果分别为：默认协作且一次执行授权；一次契约授权后连续执行；危险操作仍
单独暂停；显式额外门禁仍被遵守。

### 7.2 自动化检查

- 先增加会在现有 Skill 上失败的 Adapter 契约测试。
- 测试要求 Skill 描述完整的单次授权摘要和默认连续推进语义。
- 测试拒绝恢复“默认在 design/plan 分别暂停”的旧措辞。
- 运行 Adapter 定向测试后，再运行完整测试套件。

## 8. 验收标准

1. 未显式指定模式时不产生独立模式选择确认。
2. 默认状态变更任务在执行前只有一次授权确认。
3. 该确认同时公开模式、范围、验收、设计/计划、权限、Git 和预算。
4. 批准后默认不在设计或计划阶段再次暂停。
5. 新危险操作、范围变化、生产/敏感操作和最终验收门保持有效。
6. 显式 `design_approval`/`plan_approval` 的已有契约继续兼容。
7. Core Schema、状态机和禁止操作规则不被削弱。
