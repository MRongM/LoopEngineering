# Loop Engineering 协议与 Codex 适配器设计

- 状态：已批准设计基线
- 日期：2026-07-30
- 适用范围：当前多仓工作区及后续兼容的编码 Agent
- 首个适配器：Codex
- 首版任务来源：仅用户显式发起
- 规范仓库：`git@github.com:MRongM/LoopEngineering.git`

## 1. 背景

当前工作区由六个独立 Git 仓组成：

- `fe-super-assistant`：Electron + Vue 3 桌面端。
- `kooky-agent-hub`：Agent 注册与市场服务。
- `kooky-agent-runtime`：Run、Thread、SSE 与远程执行编排。
- `kooky-harness`：DeerFlow 与 LangGraph Server 执行框架。
- `kooky-opt`：一人团队业务与任务编排。
- `kooky-shared`：公共契约、基础设施与数据库迁移。

各仓具有独立分支、测试、架构规范和发布边界。代码任务可能涉及单仓局部改动，也可能形成跨仓契约与交付依赖。单轮提示无法稳定约束长任务中的范围、证据、权限、失败恢复和停止条件，因此需要将 AI 编码过程设计为可验证、可恢复、可停止的执行闭环。

本设计中的 Loop Engineering 指：围绕用户批准的目标契约，持续执行“行动、观察真实反馈、独立验证、修正或停止”，并以证据而非 Agent 声明判定完成。

## 2. 目标

1. 用户在每个任务开始前获知解析出的控制模式，并通过同一次执行授权确认。
2. 自动托管在明确授权范围内持续运行，无需用户逐轮提示。
3. 所有完成声明均由当前代码版本上的真实证据支撑。
4. 中高风险任务使用独立 Maker/Checker 闭环。
5. 任务可在上下文重置、进程中断或部分外部操作后恢复。
6. 危险操作、范围扩大、生产影响和合并部署保留人工门禁。
7. 支持跨仓 Git、Push 和 PR 自动化，同时保护用户现有改动。
8. Core Protocol 不绑定具体 Agent；Codex 作为首个适配器。
9. 代码生成始终遵循 KISS、YAGNI、DRY、SOLID 和仓库既有边界。

## 3. 非目标

首版明确不实现：

- 定时扫描代码、CI、Issue 或监控并自主创建任务。
- 常驻编排服务、任务市场、调度中心或可视化控制台。
- 自动合并 PR、自动部署或隐式访问生产环境。
- Agent 自行扩大任务范围、权限、预算或验收标准。
- 保存模型完整思维过程、密钥、令牌或未脱敏敏感响应。
- 用删除测试、降低断言、跳过检查或隐藏错误换取表面成功。

## 4. 核心原则

### 4.1 契约优先

任何会修改仓库或外部状态的任务都必须拥有 Loop Contract。自动模式只有在契约获得明确批准后才能启动。

### 4.2 证据优先

`DONE` 是由新鲜、可追溯的验证证据导出的状态，不是 Agent 可以自行宣告的结论。

### 4.3 最小可验证增量

每轮只选择一个尚未满足的验收条件，实施最小范围修改并立即验证，避免大批量改动后统一排错。

### 4.4 权限不扩散

自动模式只继承当前契约列明的权限。新目标、新仓库、新危险操作或扩大预算都需要契约修订与再次批准。

### 4.5 状态可恢复

对外部状态的修改前后都持久化事件。恢复时以契约、事实账本和当前仓库状态为依据，不依赖旧对话上下文。

### 4.6 独立验证

中高风险任务由独立上下文的 Checker 复核。Checker 不能直接修改生产代码，也不能降低验收标准。

## 5. 总体架构

规范分为两个层次。

### 5.1 Loop Core Protocol

Core Protocol 是 Loop 语义的唯一规则真源，负责定义：

- 契约模型与版本规则。
- 状态机和合法迁移。
- 控制模式与人工门禁。
- 风险分级与 Maker/Checker 职责。
- 预算、重试、无进展和终止规则。
- 证据、账本、恢复与最终报告模型。

Core 不包含 Codex、Claude Code 或其他工具的专有命令。

### 5.2 Codex Adapter

Codex Adapter 负责将 Core Protocol 转换为实际行为：

- 识别任务是否需要正式 Loop。
- 解析并披露控制模式。
- 调查仓库并起草契约。
- 创建账本和证据目录。
- 驱动 Maker、验证器与 Checker。
- 执行获批的 worktree、分支、提交、推送和 PR 操作。
- 在门禁或终态处停止，并输出结构化报告。

当适配器不可用时，可以退化为文档驱动执行，但不得降低安全、验收或证据标准。

## 6. 任务准入与控制模式

### 6.1 正式 Loop 的触发范围

以下任务必须进入正式 Loop：

- 功能开发、缺陷修复和重构。
- 依赖、配置、文档或生成物修改。
- 数据库、网络、外部 API 或其他状态变更。
- 分支、提交、推送、PR 等 Git 工作流。

纯问答和只读分析使用轻量的“调查、核验、报告”流程，不创建完整契约。

### 6.2 模式解析

每个正式任务必须解析为以下模式之一：

- `collaborative`：一次执行授权后，在批准范围内持续推进；进入 `DONE` 前必须通过最终人工验收。
- `autonomous`：一次执行授权后，在批准范围内持续运行到终态或硬性人工门；低/中风险任务可在无需最终人工验收的情况下进入 `DONE`，高风险任务仍需最终人工验收。

模式由 Adapter 解析，不要求用户为每个正式任务单独选择。用户显式指定模式时采用
该值；未明确指定时默认 `collaborative`。解析结果写入契约摘要，由同一次执行授权
确认。模式不继承上一个任务。

用户可随时将 `autonomous` 降级为 `collaborative`。从 `collaborative` 升级到 `autonomous` 必须明确授权并记录事件。

### 6.3 协作模式阶段门

`collaborative` 默认只在以下节点等待确认：

1. 执行前的 Loop Contract 摘要；摘要包含模式、范围、验收、关键设计决策与最小实施计划、权限、Git 目标和预算。
2. 执行中新出现且未被精确预授权的危险操作或契约实质变化。
3. 最终验收。

批准后，Agent 默认连续通过设计和计划阶段并进入执行，不再分别请求批准。只有最新
用户指令、项目规则或现有契约显式要求 `design_approval` 或 `plan_approval`
时，才保留相应额外阶段门。阶段内部不要求逐轮确认。

### 6.4 自动模式暂停条件

`autonomous` 仅在以下情况暂停：

- 新增危险操作或权限。
- 目标、范围、验收标准或预算实质变化。
- 与无法确认来源的用户改动发生冲突。
- 需要访问生产环境或传输敏感数据。
- 达到人工验收门、预算上限或无法生成必要证据。

## 7. Loop Contract

契约由 AI 根据用户目标和只读仓库调查起草。用户确认契约摘要后，契约冻结为一个版本。

### 7.1 必填字段

| 字段 | 含义 |
|---|---|
| `loop_id` | 任务唯一标识 |
| `protocol_version` | Core Protocol 版本 |
| `objective` | 单一、可验证的任务目标 |
| `mode` | `collaborative` 或 `autonomous` |
| `repositories` | 目标仓库、基准分支和允许修改范围 |
| `in_scope` | 本次必须完成的内容 |
| `out_of_scope` | 明确禁止扩展的内容 |
| `acceptance_criteria` | 可独立判定的验收条件 |
| `required_evidence` | 每条验收条件所需证据 |
| `validation_commands` | 允许且预计执行的验证命令 |
| `risk_level` | `low`、`medium` 或 `high` |
| `permissions` | 文件、网络、依赖、数据库和外部状态权限 |
| `git_policy` | worktree、分支、提交、推送和 PR 范围 |
| `budget` | 轮次、时限和 Checker 修订预算 |
| `human_gates` | 本任务额外人工门禁 |
| `assumptions` | AI 补全并公开的低风险假设 |
| `stop_conditions` | 完成、阻塞和预算耗尽条件 |

### 7.2 契约版本

- 低风险实现细节变化只记录到账本，不修改契约。
- 目标、范围、危险权限、验收标准或预算扩大时生成新版本。
- 新版本批准前，任务保持 `PAUSED`。
- 最新用户明确指令高于既有契约；若两者冲突，先修订契约再继续执行。
- 契约批准不能覆盖平台安全策略和强制性仓库规则。

### 7.3 Git 预授权

契约可以预授权以下具体操作：

- 在指定仓库和基准分支上创建隔离 worktree/分支。
- 对批准范围内、通过即时验证的增量创建提交。
- 向指定远端和分支推送。
- 向指定目标分支创建 PR。

预授权不包含强推、历史重写、`reset --hard`、自动合并或部署。目标仓库、分支、远端或操作类型发生变化时必须重新确认。

## 8. 状态机

主状态流为：

```text
INTAKE
  -> DISCOVERING
  -> CONTRACT_DRAFTING
  -> AWAITING_APPROVAL
  -> DESIGNING / PLANNING
  -> EXECUTING
  -> VERIFYING
  -> CHECKING
  -> DECIDING
      -> EXECUTING
      -> PLANNING
      -> PAUSED
      -> DONE
      -> BLOCKED
      -> BUDGET_EXHAUSTED
```

### 8.1 终态

- `DONE`：当前契约全部满足且证据完整。
- `BLOCKED`：缺少权限、必要输入或外部条件，当前无法继续。
- `BUDGET_EXHAUSTED`：达到契约或全局预算上限。

`PAUSED` 不是终态。恢复前必须记录解除门禁的授权或新增输入。

三个终态均不可原地重开。外部条件恢复或用户追加预算后，应创建关联原任务的新运行实例，并通过 `parent_loop_id` 引用原任务；旧证据只有在仍对应当前代码和环境时才可复用。

### 8.2 每轮执行

1. 从契约中选择一个未满足的验收条件。
2. 读取完成该增量所需的最小上下文。
3. 记录当前事实、假设和预期反馈。
4. 实施最小范围修改。
5. 运行与增量直接相关的验证。
6. 写入动作、结果和证据。
7. 根据风险等级进入 Checker。
8. 决定继续、修正、暂停或终止。

相同失败不得原样重复。再次尝试必须包含新的原因假设或策略。

## 9. 风险分级与 Maker/Checker

### 9.1 风险等级

| 等级 | 典型范围 | 验证要求 |
|---|---|---|
| `low` | 局部、可逆、不改变公共行为或契约 | Maker 自检并提供真实证据 |
| `medium` | 多文件行为变更、内部接口、依赖或非平凡修复 | 独立 Checker |
| `high` | 跨仓、公共契约、数据模型、迁移、安全、权限、并发、生产配置或外部副作用 | 独立 Checker + 人工最终验收 |

### 9.2 Maker

Maker 负责调查、设计、修改、即时验证和修正。Maker 不能自行关闭 Checker 发现，只能提供新证据或请求人工裁决。

### 9.3 Checker

Checker 必须：

1. 使用与 Maker 分离的上下文。
2. 独立读取契约、实际 diff 和原始证据。
3. 检查范围、架构、回归、安全和测试弱化。
4. 必要时重新运行关键验证。
5. 输出 `ACCEPT`、`REVISE` 或 `BLOCK`。

Checker 不得直接修改生产代码、扩大契约、降低验收标准或批准合并部署。

中高风险任务无法获得独立 Checker 时，不得降级为 Maker 自检后完成。

## 10. 验证证据与完成定义

### 10.1 证据字段

每条证据至少包含：

- 验收条件 ID。
- 实际命令与工作目录。
- 执行时间、退出码和结果摘要。
- 对应提交、工作树或 diff 指纹。
- 测试报告、日志、截图或产物路径。
- 证据生成者和 Checker 结论。

### 10.2 验证规则

- Bug 修复尽可能保留修复前失败和修复后通过的成对证据。
- 新功能优先使用契约测试或行为测试。
- 无法自动测试时，必须定义可重复的替代验证。
- 最终相关代码变更后必须重新运行受影响验证。
- 旧代码版本上的结果视为过期。
- Flaky 测试必须明确分类和记录，不能重复运行直到偶然通过。
- 不要求运行与改动无关的全量检查，但必须覆盖实际影响范围。

### 10.3 DONE 条件

只有同时满足以下条件才能进入 `DONE`：

1. 所有验收条件都有当前代码版本上的新鲜证据。
2. 所有必须检查项通过。
3. 中高风险任务获得 Checker 的 `ACCEPT`。
4. 所有 `collaborative` 运行和高风险任务已通过人工最终验收门。
5. 没有未解决门禁、范围漂移或用户改动冲突。
6. 实际 diff 与批准范围一致。
7. 契约要求 Git/PR 自动化时，提交已推送且 PR 已创建。
8. 已生成最终证据摘要、已知限制和未执行检查说明。

`DONE` 表示交付已准备好接受人工合并，不表示已经合并或部署。

## 11. 失败恢复与预算

### 11.1 失败分类

- `CODE`：实现缺陷。
- `TEST`：测试、断言或验收不满足。
- `TOOL`：命令、工具或权限失败。
- `ENVIRONMENT`：依赖、服务、平台或网络条件不满足。
- `CONTRACT`：目标、范围或验收条件矛盾。
- `CONFLICT`：用户修改、其他任务或远端分支冲突。
- `EXTERNAL`：依赖人工、第三方或生产环境状态。

### 11.2 恢复规则

- 同一失败最多按原策略重试一次。
- 连续两轮没有新增证据或实质进展时停止盲目执行并转入诊断。
- 不回滚、覆盖或删除无法确认来源的用户改动。
- 中断恢复时先核对工作树、分支、远端和证据有效性。
- 已产生的提交、推送、PR 或外部副作用必须记录，不能假设操作原子成功。
- 契约矛盾进入 `PAUSED`，外部条件缺失进入 `BLOCKED`，预算耗尽进入 `BUDGET_EXHAUSTED`。

### 11.3 默认预算

| 风险 | 最大执行轮次 | 默认时限 | Checker 修订轮次 |
|---|---:|---:|---:|
| 低 | 3 | 30 分钟 | 0 |
| 中 | 6 | 90 分钟 | 2 |
| 高 | 10 | 180 分钟 | 3 |

全局硬上限为 12 个执行轮次或 4 小时。超过硬上限时必须输出当前证据、未完成项和继续建议，由用户重新授权。

一次执行轮次从进入 `EXECUTING` 开始，到 `DECIDING` 产生下一状态结束。Maker 修正会开启新轮次；单独读取上下文、记录事件或等待人工输入不消耗执行轮次。

## 12. 持久化模型

协议源码与运行状态分离。

### 12.1 运行目录

```text
<workspace>/.loop-runs/<loop_id>/
├── contract.yaml
├── state.json
├── events.jsonl
├── evidence/
└── final-report.md
```

- `contract.yaml`：当前批准契约。
- `events.jsonl`：只追加事实账本。
- `state.json`：可由事件重建的当前快照。
- `evidence/`：脱敏验证输出和产物索引。
- `final-report.md`：终态报告。

### 12.2 事件要求

每个事件包含：

- 单调递增序号和事件 ID。
- Loop、契约版本、时间和 Actor。
- 状态迁移、动作、结果和失败分类。
- 证据引用和预算消耗。
- 权限、批准或拒绝变化。

任何外部状态修改都先追加意图事件，执行后再追加结果事件。若进程中断在两者之间，恢复流程必须先核对真实外部状态，再决定补记结果、重试或进入 `PAUSED`。

事件追加与状态快照替换必须使用原子文件操作。恢复时必须检测事件缺失、重复、乱序、尾部半写入或损坏。账本不保存密钥、令牌、完整模型思维过程或未脱敏响应。

运行账本默认不提交到业务仓，也不自动删除。

## 13. Git 与跨仓交付

### 13.1 启动检查

执行 Git 自动化前必须只读确认：

- 目标仓库和基准分支存在。
- 当前工作树和用户修改状态。
- 远端名称、目标分支和访问能力。
- 跨仓依赖顺序。

### 13.2 执行规则

- 按契约创建隔离 worktree/分支。
- 不覆盖或回滚现有用户修改。
- 每个通过即时验证的独立增量形成原子提交。
- Checker 修订使用后续修复提交，不改写已推送历史。
- 完整验证通过后推送并创建 PR。
- 跨仓任务分别创建分支和 PR，在 PR 中记录依赖图和合并顺序。
- 禁止强推、历史重写、`reset --hard`、绕过检查、自动合并和自动部署。

### 13.3 完成边界

如果契约要求 PR，创建并返回 PR 地址是 `DONE` 的必要条件。PR 合并和部署始终位于 Loop 外部的人工门禁之后。

## 14. Codex 适配器交互

### 14.1 入口

1. 判断请求是否会修改状态。
2. 解析控制模式；显式指定则采用，否则默认 `collaborative`，不单独询问。
3. 只读调查仓库、规范和近期变更。
4. 起草契约、风险等级、关键设计决策与最小实施计划。
5. 展示模式、目标、范围、验收、设计、计划、预算、权限和 Git 摘要。
6. 获得明确批准后启动。

### 14.2 运行

- 在阶段边界或长时间执行期间提供简短进度心跳。
- 用户新消息优先于当前执行。
- 新消息属于范围内补充时记录事件；实质改变目标时修订契约。
- 自动模式在硬门禁处暂停，不通过猜测扩大权限。
- Checker 仅在风险等级要求时使用独立 Agent/上下文。

### 14.3 最终报告

最终报告包含：

- 终态与终态原因。
- 契约各验收条件的结论。
- 修改文件、提交、分支和 PR。
- 验证证据和 Checker 结论。
- 预算消耗和失败恢复摘要。
- 已知限制、未执行检查和人工后续动作。
- KISS、YAGNI、DRY、SOLID 的落实说明。

## 15. 代码生成质量规则

### 15.1 通用规则

- 先读后写，理解既有实现、测试和约束。
- 优先最简单、最直接且满足契约的方案。
- 不开发当前验收条件未要求的未来能力。
- 消除修改范围内已经形成的实质重复，不为可能出现的重复提前抽象。
- 保持职责、依赖方向和接口边界清晰。
- 不进行无关重构、批量格式化或依赖升级。
- 注释语言与代码库一致，注释解释原因和约束。
- 新依赖必须说明必要性、替代方案和授权来源。

### 15.2 规则优先级

发生冲突时按以下顺序处理：

1. 平台强制安全策略和最新用户明确指令。
2. 当前批准的 Loop Contract。
3. 当前目录及父目录的 `AGENTS.md`。
4. 仓库的 `CLAUDE.md`、架构文档和测试约定。
5. Loop Core Protocol 默认规则。

最新用户指令与已批准契约冲突时，不直接执行冲突内容，而是暂停并修订契约。

### 15.3 当前工作区 Profile

- 微服务不得直接导入其他服务源码。
- 跨服务通过 HTTP internal RPC 或既有 Port 抽象交互。
- 公共数据契约和数据库迁移由 `kooky-shared` 管理。
- `kooky-agent-runtime` 与 `kooky-harness` 保持远程调用边界。
- 前端遵循现有 Vue/Electron 结构，不把服务端职责迁入客户端。
- 每个仓继续遵循自身 `AGENTS.md` 和 `CLAUDE.md`。

## 16. 安全门禁

危险操作请求使用统一格式：

```text
⚠️ 危险操作检测！
操作类型：[具体操作]
精确目标：[仓库、分支、文件、数据库或环境]
影响范围：[将发生的状态变化]
风险评估：[最坏后果与恢复难度]
恢复方案：[可用的回滚或补救措施]
当前证据：[为什么需要执行]

请确认是否继续？[需要明确的“是”“确认”“继续”]
```

执行约束：

- 契约预授权只覆盖已经解析到精确目标的操作。
- 危险命令不得依赖未校验环境变量、宽泛 glob 或工作区根路径。
- 执行前重新确认目标仍与批准时一致。
- 敏感信息不得进入输出、账本、提交或 PR。
- 沙箱或权限失败只能请求必要授权，不得规避安全控制。
- 数据库迁移必须提供前向方案、兼容性分析和恢复策略。
- 生产调用、合并和部署不能由普通自动契约隐式授权。
- 所有批准、拒绝和权限变化都写入追加式账本。

## 17. 文件布局与所有权

Core Protocol 的规范所有者是独立的 `LoopEngineering` 仓库，远端为 `git@github.com:MRongM/LoopEngineering.git`。规划结构如下：

```text
LoopEngineering/
├── PROTOCOL.md
├── schemas/
│   ├── loop-contract.schema.json
│   ├── loop-state.schema.json
│   └── loop-event.schema.json
├── templates/
│   ├── contract.yaml
│   └── final-report.md
├── adapters/
│   └── codex/
│       ├── SKILL.md
│       └── scripts/
└── docs/
    └── superpowers/specs/
```

`LoopEngineering` 只负责协议、Schema、模板、适配器和测试，不承担业务服务职责。目标业务仓仅保存必要接入配置，不复制 Core 规则。

当前设计文档可以先在工作区暂存，但批准后的规范资产必须复制到该规范仓维护。创建提交和推送属于独立危险操作，必须获得精确授权。

## 18. 测试策略

### 18.1 测试层次

- Schema 测试：必填字段、枚举、版本和非法输入。
- 状态机测试：合法迁移、非法跳转、终态不可变和暂停恢复。
- 门禁测试：危险操作、范围扩大、权限不足和模式升级。
- 预算测试：轮次、时间、重复失败和 Checker 修订上限。
- 恢复测试：执行中断、部分写入、损坏事件和外部操作半成功。
- 安全测试：脱敏、路径边界、命令目标解析和权限不扩散。
- Git 集成测试：使用临时仓库与本地模拟远端。
- 端到端测试：协作低风险、自动中风险、跨仓高风险、门禁暂停、预算耗尽和用户冲突。

### 18.2 发布门槛

- Core Protocol 与 Schema 使用语义化版本。
- Adapter 显式声明兼容协议版本。
- 不兼容时拒绝启动，而不是静默降级。
- 状态机、门禁、安全和恢复测试必须全部通过。
- 首次启用自动模式前完成无外部副作用的 dry-run。
- 测试不得依赖真实生产环境、真实合并或真实部署。
- 协议修改必须提供迁移说明，运行中的旧契约不得静默升级。

## 19. 建议实施顺序

本设计批准后，实施计划应按以下垂直切片拆分：

1. Core 文档、契约 Schema、状态 Schema 与验证器。
2. 追加式事件账本、状态投影和恢复。
3. Codex 入口、两种模式和人工门禁。
4. Maker/Checker 与证据收集。
5. 隔离 Git、Push 和 PR 自动化。
6. 安全、故障恢复和端到端测试。
7. 先 dry-run，再开放低风险自动模式，最后开放中高风险任务。

每个切片必须独立可测试，不提前实现任务发现、调度平台或自动合并部署。

## 20. 设计验收标准

本设计被视为可进入实施计划，当且仅当：

1. 两种控制模式及切换规则无歧义。
2. 自动模式的权限、暂停与终止条件可机器判定。
3. 契约字段足以约束目标、范围、证据、预算和 Git 行为。
4. Maker/Checker 边界和风险分级明确。
5. `DONE` 不能在缺少新鲜证据时产生。
6. 中断恢复不依赖旧对话上下文。
7. 用户改动、危险操作、生产环境、合并和部署受到保护。
8. Core 与 Codex Adapter 可以独立演进。
9. 首版范围不包含主动任务发现和常驻编排平台。
10. 协议本身具有可执行的测试与发布门槛。

## 21. 已确认决策

- 使用工具无关 Core Protocol，并优先实现 Codex Adapter。
- 采用 `collaborative` 和 `autonomous` 二档模式。
- AI 起草完整契约，用户一次批准后自动执行。
- 使用标准安全门禁和风险分级 Checker。
- 使用双重预算与可恢复执行账本。
- 首版仅接受用户显式发起任务。
- 采用风险适配的证据优先开发方式。
- 支持完整 Git、Push 和 PR 自动化。
- 自动合并和部署不在授权范围。
- 使用独立 `loop-engineering` 控制仓承载协议资产。

本设计不存在待定行为契约。具体语言、库和脚本结构由后续实施计划在不改变上述行为契约的前提下确定。
